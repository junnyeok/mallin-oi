# 이벤트 일정 알람 — 앱 전용 설정과 웹 다운로드 안내

2026-09-26 최신 정책. 알람 선택·예약은 네이티브 앱에서만 사용한다.
웹에서는 알람 설정을 누르면 앱 전용 기능 및 다운로드 안내를 표시한다.
**예**는 Android에서 Google Play, 그 외 환경(iPhone·iPad·PC)에서 App Store의 말린오이 캘린더 페이지를 새 탭으로 연다.
**아니오**는 안내창만 닫고 편집 중인 일정을 유지한다. Escape·바깥 영역 클릭도 닫기로 동작한다.
웹에서는 알람 선택·권한 요청·파일 다운로드·알람 저장을 하지 않으며, 이전 웹 알람 저장값도 읽거나 수정하지 않는다.
이 정책이 이전 웹 ICS 가져오기 동작을 대체한다. 앱의 스크롤 선택·최대 두 알람·일정 저장 연동은 유지한다.

## 사용 방법

새 일정 또는 저장된 이벤트 일정을 열면 메모 아래에 **알람 → 알람 설정**이 나온다.
다른 항목과 같은 높이·구분선·글자색을 사용한다. **앱에서** 누르면 아래 항목이 세로 스크롤 메뉴로 열린다.

없음 / 이벤트 시간 / 5분 전 / 10분 전 / 15분 전 / 30분 전 / 1시간 전 /
2시간 전 / 1일 전 / 2일 전 / 1주 전.

- 첫 알람을 고르면 **두 번째 알람** 행이 나타난다. 최대 두 개이며 같은 시각은 중복 등록하지 않는다.
- 첫 알람을 없음으로 바꿀 때 두 번째도 비어 있으면 두 번째 행이 사라진다.
  두 번째가 지정돼 있으면 남은 알람을 첫 행으로 이동한다.
- 메뉴 선택은 편집 중인 값이다. 일정의 저장(새 일정은 완료)을 눌러야 등록·교체·해제된다.
  저장하지 않고 닫으면 기존 예약을 유지한다.
- 앱에서 처음 설정할 때 **알람을 허용할까요? / 취소 / 허용**을 표시한다.
  허용은 OS 권한 요청 후 공개 API로 휴대폰의 앱 설정을 연다. 돌아와 알람을 고르고 일정을 저장한다.
  권한이 꺼져 있으면 다음 설정 시 다시 안내하며, 필요한 권한 없이 알람 예약 성공으로 표시하지 않는다.
- 18:00 가족식사참치회에 5분 전·10분 전을 고르면 같은 날짜 17:55·17:50에 예약한다.
  안내 문구는 **‘가족식사참치회’ 일정이 5분 남았어요!**이고, 이벤트 시간은 **일정이 시작돼요!**이다.
- 제목·시작 시간을 검증한다. 이미 지난 알람 시각은 제외하고 저장 후 안내한다.
- 같은 기기에서 상세 화면의 제목·시간을 수정하고 저장하면 예약을 교체한다.
  상세 화면에서 일정을 삭제하면 해당 기기의 알람도 해제한다.

## 환경별 동작

| 환경 | 동작 |
| --- | --- |
| iOS 26 이상 | AlarmKit 시스템 알람. 기본 시계 앱 목록에는 추가하지 않는다 |
| iOS 26 미만 지원 버전 | 소리 있는 로컬 알림. 기기의 알림·집중 모드 설정을 따른다 |
| Android | 날짜를 포함한 AlarmManager 알람과 소리 있는 알림. 알림·정확한 알람 권한을 확인한다 |
| 웹 | 앱 전용 알람 안내. 예 → 앱 스토어, 아니오 → 안내창 닫기. 실제 알람 처리는 하지 않는다 |

알람 선택과 예약은 **이 기기**에 저장하며 서버·다른 기기로 자동 동기화하지 않는다.
다른 기기 또는 다른 사용자가 공유 일정을 변경·삭제한 경우까지 알람을 자동 동기화하지 않는다.
이전 버전에서 이미 외부 캘린더에 가져온 알림은 해당 캘린더에서 관리한다. 웹은 휴대폰의 앱 알람 권한을 직접 열 수 없다.
Android 기본 시계 앱 연결·1분 전·시간 직접 지정 UI는 이번 선택지에서 제거했다.
Android 소리는 기기의 알람 음량·알림·방해금지 설정을 따르며 강제 중지 상태까지 보장하지 않는다.

iOS는 UIApplication.openSettingsURLString을 사용한다. **이번 시뮬레이터에서는 설정 앱 첫 화면이 열렸다.**
물리 iPhone에서 앱별 설정 화면까지 바로 이동하는지, 해당 OS의 알람 권한 표시 위치는 실기기 확인이 남아 있다.
Android는 필요한 상태에 따라 앱 알림 설정 또는 정확한 알람 설정으로 이동한다.

## 저장·오류 처리

- 알람 입력·권한 검증 → 일정 저장 RPC 성공 → 네이티브 예약 교체 순서다.
- 일정 저장이 실패하면 네이티브 예약을 변경하지 않는다.
- 새 알람들을 먼저 예약하고 기존 알람을 해제한다. 두 번째 새 예약이 실패하면 방금 만든 예약을 정리하고 이전 예약을 보존한다.
- 일정은 저장됐지만 OS 반영이 실패하면 그 사실을 표시하고 편집창을 유지한다.
  새 일정 저장 후 재시도는 반환된 일정 ID를 재사용해 중복 생성을 피한다.
- OS 예약과 서버 저장은 하나의 트랜잭션이 아니므로 등록/취소 실패는 사용자에게 표시한다.
- 이전 단일 알람은 시작 시각과 차이를 계산해 새 선택지로 불러온다.
  이전 1분 전·임의 시각처럼 새 선택지에 없는 경우 다시 선택하라는 안내를 표시한다.

## 구현 위치

- 공통 입력 행: `assets/js/modules/calendar-entry-sheet.js`, `assets/css/components/calendar-entry-sheet.css`.
- 이벤트 저장·삭제 연결: `assets/js/modules/event-calendar.js`.
- 선택지·시간 계산·안내 문구: `assets/js/modules/event-alarm.js`.
- 웹 다운로드 안내의 스토어 주소: 기존 `assets/js/modules/calendar-app-download-popup.js`의 주소를 재사용한다.
- 스크롤 메뉴·권한 안내·두 알람 편집: `assets/js/modules/event-alarm-picker.js`.
- iOS: `ios/App/App/EventAlarmsPlugin.swift`.
- Android: `EventAlarmsPlugin.java`, `EventAlarmStore.java`, `EventAlarmReceiver.java`.
- Android는 재부팅·시간 변경·권한 재허용 시 저장된 미래 알람 재예약 경로를 유지한다.
- 이번 관련 원본 6개(JS 4개·CSS·사이트 버전)만 `www`·양 플랫폼 `public`으로 범위 동기화한다.
  혼합 작업 트리 보존을 위해 www 전체 재생성은 실행하지 않았다.

## 이번 웹 안내 변경에서 직접 검증한 결과

- 캘린더·위젯 관련 Node 검사 102/102, 알람 단위 검사 9/9 통과.
- 로컬 브라우저 데스크톱 1280×720 및 모바일 390×844에서 안내창·예/아니오·포커스 이동을 확인했다.
- 아니오는 안내창만 닫고 일정 편집을 유지한다. 예를 누르면 실제 말린오이 캘린더 App Store 페이지가 새 탭으로 열린다. Google Play 주소도 실제 앱 페이지로 연결되는 것을 확인했다.
- 잘못된 이전 웹 알람 저장값이 있어도 일반 일정 저장은 성공했다. 알람 등록·권한 설정 이동·파일 다운로드는 각각 0회이고 기존 웹 알람 저장값은 변경되지 않았다. `?app=calendar`만 붙인 웹에서도 앱 전용 안내가 유지된다.
- 네이티브 모의 브리지에서 5분·10분 알람 두 개를 선택하고 저장하면 권한 설정 이동 1회, 예약 1회, 올바른 두 알람 시각·안내 문구가 전달된다. 실제 휴대폰 재검증은 아니다.
- 관련 JS 문법·HTTP 200 응답 8개·원본/www/Android/iOS public 6개 파일의 바이트 일치를 확인했다. 검증 페이지 콘솔 오류는 없었다.
- 기존 동시 변경을 포함한 작업 폴더 전체 검사는 303개 중 302개 통과했다. 남은 실패는 기존 프로필 오디오 모듈의 native public 불일치이며 이번 커밋에 포함하지 않는다. 커밋 후 깨끗한 스냅샷의 검사 결과는 완료 보고에 별도로 기록한다.
- 이번 웹 변경에 네이티브 코드·앱 버전·SQL·사용자 제공 에셋 수정은 없다. 실제 계정 데이터는 사용하지 않았다.

## 앞선 앱 알람 구현에서 검증한 기록 (이번 웹 안내 변경 전)

- Node 캘린더·위젯·알람 검사 **103/103 통과**. 알람 검사 10개에는 새 선택지,
  최대 두 개/중복/없음 처리, 시각 계산, 안내 문구, 지난 시각 제외, 두 VALARM 파일 검사가 포함된다.
- Xcode 26.6 / iOS Simulator 26.5 Debug 빌드 성공. 배포 Archive가 아니다.
- iPhone 17 시뮬레이터: 앱 권한 안내에서 설정 앱으로 이동 후 돌아와 메뉴를 이어서 선택했다.
  5분 전·10분 전 선택 후 저장 → OS 조회 activeCount 2 → 해제 후 activeCount 0을 확인했다.
- 별도의 짧은 예약이 앱 백그라운드 상태에서 실제 시스템 알람 배너로 표시됨을 확인했다.
  OS에 전달된 문구는 ‘가족식사참치회’ 일정이 5분 남았어요!이다. 작은 배너에서는 끝부분이 줄임 표시된다.
  검증 알람은 종료·해제했고 일반 로컬 앱을 다시 설치했다. 앱 데이터는 삭제하지 않았다.
- Android Debug APK / instrumentation APK / lintDebug 성공. Pixel 7 에뮬레이터의 네이티브 검사 **2/2 통과**.
  실제 AlarmManager 전달·메시지/반복 소리 플래그·해제, 두 예약과 두 번째 예약 실패 시 이전 예약 보존을 확인했다.
- Android lint에는 알람 알림 터치가 해제 전용 BroadcastReceiver를 호출한다는 기존 권고가 남는다.
  receiver가 Activity를 시작하지 않으므로 알림 trampoline은 만들지 않는다.
- 브라우저: 권한 안내 취소·허용, 11개 스크롤 선택지, 첫 알람 해제 시 두 번째 행 숨김,
  저장 시 두 알람과 올바른 메시지 전달, 일정 저장 오류 시 편집창 유지/오류 표시,
  권한 거부 시 저장 차단, 저장 없이 닫으면 선택 취소, 메뉴 마지막 1주 전 선택을 확인했다.
  브라우저 네이티브 동작은 명시적 mock이고 실제 OS 검증은 위 시뮬레이터·에뮬레이터 결과와 구분한다.
- 일반 로컬 iOS 앱에서도 기존 가족식사참치회 일정의 새 메뉴·두 번째 알람 행을 확인했다.
  선택은 저장하지 않고 닫아 실제 일정과 예약을 변경하지 않았다.
- 원본 5개 파일과 www·iOS·Android public, 최종 iOS App.app·Android APK의 바이트 일치를 확인했다.

실제 계정의 일정을 만들거나 수정·삭제하는 검증은 하지 않았다.
물리 iPhone/Android, iOS 26 미만 알림 실행, 재부팅 후 재예약은 미확인이다.
인수인계 당시의 profile.js 생성본 불일치와 네이티브 public 버전 메타데이터 차이는 보존했다.

## 다시 확인할 때

```bash
node --test tests/calendar-*.test.mjs tests/study-widget-completion.test.mjs
```

로컬 검증 페이지: `/tests/fixtures/event-alarm-browser.html`.
`?mock=success`, `?mock=denied`, `?mock=save-error`, `?mock=alarm-error`는 브라우저의 명시적 mock이다.
검증 페이지는 준비 스크립트의 복사 대상이 아니며 운영 앱에는 포함하지 않는다.
네이티브 검증은 저장소 밖 임시 앱 사본에 이 페이지를 넣어 수행한 후 일반 앱으로 복귀한다.
실기기에서는 알람 두 개를 고른 뒤 저장하고 잠금 화면·안내 문구·소리·수정/해제를 확인한다.
